# Data Warehouse Naming Conventions

This document outlines the formal naming conventions and architectural governance rules applied across all layers (Bronze, Silver, Gold) and database objects within the Data Warehouse project.

---

## 1. General Principles

- **Casing Standard**: All database objects (schemas, tables, views, columns, procedures) must use `snake_case` (lowercase letters separated by underscores `_`).
- **Language**: English is the mandatory language for all technical identifiers and descriptions.
- **Reserved Words**: Avoid using SQL/T-SQL reserved keywords (e.g., `user`, `date`, `order`, `table`) as column or object names.
- **Explicit Schema Scoping**: Every object must be created under its explicit Medallion schema (`bronze.`, `silver.`, `gold.`).

---

## 2. Table & View Naming Rules

### Bronze Layer (`bronze.`)
- **Rule**: Mirror raw source entities. Names must retain their original table/file identity prefixed by the source system identifier.
- **Pattern**: `<source_system>_<source_entity>`
- **Source Systems**:
  - `crm`: Customer Relationship Management System
  - `erp`: Enterprise Resource Planning System
- **Examples**:
  - `bronze.crm_cust_info`
  - `bronze.erp_loc_a101`

### Silver Layer (`silver.`)
- **Rule**: Keep structural alignment with Bronze entities while representing cleansed, standardized, and typed datasets.
- **Pattern**: `<source_system>_<source_entity>`
- **Examples**:
  - `silver.crm_cust_info`
  - `silver.erp_cust_az12`

### Gold Layer (`gold.`)
- **Rule**: Business-aligned dimensional star schema models. Tables and views must be named by their dimensional role followed by the business entity name.
- **Pattern**: `<category>_<entity>`

| Prefix | Role / Meaning | Examples |
| :--- | :--- | :--- |
| `dim_` | Dimension View/Table (Conformed dimensions) | `gold.dim_customers`, `gold.dim_products` |
| `fact_` | Fact View/Table (Transactional metrics) | `gold.fact_sales` |
| `report_` | Aggregated / Reporting Datasets | `gold.report_monthly_sales` |

---

## 3. Column Naming Rules

### Business & Natural Keys
- **Natural Keys**: Original identifiers from source systems retain their domain-specific names in Bronze/Silver (e.g., `cst_id`, `prd_key`).

### Surrogate Keys
- **Rule**: All primary surrogate keys in Gold dimension views must end with the suffix `_key`.
- **Pattern**: `<entity_singular>_key`
- **Examples**:
  - `customer_key` in `gold.dim_customers`
  - `product_key` in `gold.dim_products`

### Foreign Keys
- **Rule**: Foreign keys referencing dimensions in fact views must strictly match the surrogate key name of the target dimension table.
- **Examples**:
  - `customer_key` in `gold.fact_sales` (references `gold.dim_customers.customer_key`)
  - `product_key` in `gold.fact_sales` (references `gold.dim_products.product_key`)

### Technical Audit Columns
- **Rule**: Metadata columns generated by the ETL process must begin with the `dwh_` prefix.
- **Examples**:
  - `dwh_create_date`: Timestamp when the record was inserted into the Data Warehouse (`DATETIME2`).

---

## 4. Stored Procedure & Script Naming Rules

Stored procedures and automation scripts must reflect their functional layer or operational purpose:

- **ETL Pipeline Procedures**:
  - `load_bronze`: Bulk loading raw source files into Bronze tables.
  - `load_silver`: Cleansing, transforming, and loading data into Silver tables.
  - `load_gold`: Building Gold dimensional views and star schema layers.

- **Data Quality & Testing Scripts**:
  - **Pattern**: `check_<source_system>_<entity>.sql`
  - **Example**: `check_crm_cust_info.sql` (Verifies primary keys, nulls, and domain integrity).
